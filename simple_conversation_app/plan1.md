# LLM 実装プラン — STT結果から博多弁の応答テキストを生成

## ゴール

STT(Whisper)が書き起こしたユーザー発話を OpenAI API に渡し、
博多弁の応答テキストを生成する。まずはログ出力まで(TTS・発話は次フェーズ)。

## モデル選定(2026年7月時点の公式Pricingより)

現行ラインナップの軽量・低価格帯(価格は $/1Mトークン、Standard・短コンテキスト):

| モデル | Input | Cached input | Output | 評価 |
|---|---|---|---|---|
| **gpt-5.4-mini(採用)** | $0.75 | $0.075 | $4.50 | 品質と価格のバランス。方言のニュアンスも安定 |
| gpt-5.4-nano | $0.20 | $0.02 | $1.25 | 最安・最速。ただし方言の再現が単調になりがち |
| gpt-5.6-luna | $1.00 | $0.10 | $6.00 | 最新世代の廉価版。mini比で割高、この用途には過剰 |

**推奨: `gpt-5.4-mini`**。理由:

- 会話1往復のコストが約0.01円(下記試算)で、mini と nano の差額は実質無意味。
  それなら方言の自然さで上の mini を選ぶ
- 応答は1〜2文しか生成しないので Output 単価の差も効かない
- nano はフォールバック / 比較用に設定で切替可能にしておく

### コスト試算(gpt-5.4-mini)

1往復あたり: システムプロンプト ~300 + 履歴 ~200 + ユーザー発話 ~50 トークン入力、
応答 ~80 トークン出力 → **約 $0.00008(0.01円強)/往復**。
システムプロンプトと履歴は prompt caching が効くため(Cached input $0.075)実際はさらに下がる。
ワークショップで1日中動かしても数円のオーダー。

## API 設計

- **Responses API**(現行の推奨API)+ `openai` Python SDK を使用
- `reasoning: {"effort": "minimal"}` を指定(gpt-5.4系は既定で推論するため、
  雑談用途では推論をほぼ切って応答レイテンシを削る)
- `max_output_tokens: 150` 程度に制限(短い応答の強制 + コスト上限)
- APIキーは既存の `.env`(リポジトリ直下)から `OPENAI_API_KEY` を読む

```python
from openai import OpenAI

client = OpenAI()
resp = client.responses.create(
    model="gpt-5.4-mini",
    instructions=SYSTEM_PROMPT,
    input=history + [{"role": "user", "content": text}],
    reasoning={"effort": "minimal"},
    max_output_tokens=150,
)
reply = resp.output_text
```

## システムプロンプト(博多弁)

```
あなたは福岡のエンジニアカフェにいる小型ロボット「Reachy Mini」たい。
来場者と博多弁で気さくに雑談する。

ルール:
- 必ず博多弁で話す。「〜と?」「〜ばい」「〜たい」「〜けん」「〜っちゃん」
  「〜しとう」「よかよ」などを自然に使う。わざとらしい誇張はせん
- 音声で読み上げる前提。1〜2文、50文字以内で短く話し言葉で答える
- 箇条書き・記号・絵文字・英語は使わない
- 入力は音声認識の結果やけん、誤変換があっても文脈で補って解釈する
- わからんことは正直に「わからんばい」と言う

例:
ユーザー「今日は何ができると?」
→「おしゃべりできるばい。なんか聞きたいことあると?」
```

ポイント: 方言例を語尾リストで与える(モデル任せにすると標準語混じりになる)、
音声認識誤りの許容を明示、読み上げ前提の短文制約。

## アーキテクチャ(main.py への追加)

```
[STTスレッド] 書き起こし完了 → llm_queue に put
        ↓ queue.Queue
[LLMスレッド(新規)] OpenAI API 呼び出し → 応答テキストをログ出力
```

- STTスレッドで直接APIを呼ばない: ネットワーク待ち(0.5〜2秒)中に次の発話の
  STTが詰まるのを防ぐ
- **会話履歴**: `deque(maxlen=10)`(5往復)で user/assistant ペアを保持。
  システムプロンプトは固定なので prompt caching が効く
- **割り込み対応(シンプル版)**: LLM応答待ちの間に新しいSTT結果が来たら、
  古いリクエストの結果は捨てて最新だけ処理(queue を覗いて最新以外 skip)
- **エラー処理**: タイムアウト10秒、失敗時はログに警告を出して会話継続
  (ワークショップ中にAPI障害で全体が止まらないように)
- `--no-llm` フラグで STT まで(従来動作)に切替可能にする

## 実装ステップ

1. `pip install openai`、`.env` の `OPENAI_API_KEY` 確認
2. `llm_worker()` スレッド + `llm_queue` を追加、STTスレッドから接続
3. システムプロンプト・履歴管理・エラー処理を実装
4. 動作確認後、必要ならモデルを `gpt-5.4-nano` に切替えて品質比較

## 検証手順

1. 単体テスト: 固定テキスト「今日の天気を教えて」で博多弁応答が返ること
2. 通し: 話す → STT → 博多弁応答がログに出るまでの遅延を計測(目標2秒以内)
3. 5往復して履歴が効いていること(前の発言を踏まえた応答)
4. 標準語が混ざらないか、長文になりすぎないかを確認し、プロンプトを調整
5. Wi-Fi遮断状態でエラーになっても VAD/モーションが動き続けること
